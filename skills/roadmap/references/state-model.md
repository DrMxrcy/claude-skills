# Roadmap state model

## Source of truth
- **Plan files** (`.roadmap/plans/NNN-slug.md`) — progress (the checklist) + frontmatter.
- **`.roadmap/config.json`** — project, currentVersion, nextId, item registry, settings.
- **`ROADMAP.md`** — rendered view; the region between `<!-- roadmap:auto:start -->` and `<!-- roadmap:auto:end -->` is regenerated by `sync` (including the current-version line and per-version breakdown). Fully-done versions strictly below `currentVersion` collapse to a one-line summary unless `settings.collapseShipped` is `false`. Everything else (title, Idea Incubator) is free-form and never rewritten by scripts — `idea`/`remove` only append single bullets under the Idea Incubator heading.
- **Incubator location** — bullets live under the Idea Incubator heading in `ROADMAP.md` by default, or in the external file named by `settings.incubatorFile` (usually `.roadmap/IDEAS.md`, created by `tidy --externalize`, which leaves one linked bullet on the dashboard). `idea`/`promote`/`remove` resolve the location via `incubator_file()`; `tidy` analyzes both.
- **`.roadmap/runs.jsonl`** — run log (plan 38): one JSON object per line per merge-gate or suite run, written only by `run` (append under a lock; trimmed to the newest `settings.runsKeep`, default 200). Committed. Concurrent appends on two branches merge by union via the `.roadmap/runs.jsonl merge=union` line that `init`/`upgrade` add to `.gitattributes`. Readers skip an unparseable line with a warning (`status --json` `runWarnings`), never fail.
- **`.roadmap/notes/*.md`** — long-form idea write-ups created by `idea --body/--body-file`, linked from their incubator bullet. Not tracked in the registry.

## config.json
```json
{"project":"NAME","currentVersion":"0.0.1","nextId":1,
 "items":[{"id":1,"slug":"auth-setup","title":"Auth setup","type":"feature",
           "version":"0.0.1","file":"plans/001-auth-setup.md"}],
 "versionDates":{"0.0.1":"2026-07-09"},
 "settings":{"autoCommit":true,"gitTagOnRelease":false,"collapseShipped":true,
             "autoRelease":"nudge"}}
```
- `versionDates` — stamped by `sync` the first time a version hits 100% (stable changelog/collapse dates).
- `settings.collapseShipped` — defaults to `true` when absent. With it `false` and the auto block over 150 lines, `orient`/`tidy` suggest turning it back on (the auto block never triggers the free-form length warning).
- `settings.autoRelease` — `off` | `nudge` (default when absent) | `auto`: what happens when the current version is 100% but uncut (nudge prints a release reminder from `check`/`next`/`orient`; auto runs `release` when a target version is known).
- `settings.requireEvidence` — defaults to `false`; when `true`, `check` refuses without `--evidence "<verify command + result>"` (`--undo` is never gated).
- `settings.requiredSections` — per-type override of the plan sections `check` requires to be filled (`{"bug":["Observed","Root Cause","Acceptance"],"feature":["Core objective","Acceptance"],…}`; defaults: bug = Observed, Root Cause, Acceptance; feature/chore/refactor = Core objective, Acceptance). A name matches a `##` heading (emoji-insensitive prefix) or else a `**Label:**` bullet. While one is still template — empty, a bare `-`, an unfilled `**Label:**`, or a whole-value `<…>` placeholder — `check` refuses (naming the sections and file) unless `--force`, which records `forced past empty template (…)` in the evidence line; `--undo` is never gated. A required section the plan lacks entirely is skipped (older plans stay checkable) unless the type is listed here explicitly; `[]` turns the gate off for that type. `tidy` lists unfinished stub plans (report-only).
- `settings.requireAcceptance` — default `false` for existing projects (absent = off, so nothing changes until you opt in); `init` writes `true` for new projects. When on, the `check` that would **complete** an item (every step ticked, at least one by this check) is refused while any ✅ Acceptance criterion is unmarked or failed; the refusal lists them with their numbers. `--force` checks anyway and records `forced past unaccepted acceptance (#2, #4)` in the evidence line. Checks that leave a step open, `--undo`, and `Fails if:` guards are never gated. Waiting steps (`[~]`) never count as ticked, so a check that leaves one open does not trip the gate.
- `settings.buildRoles` — optional map of quality-first build roles to model/agent names (`{"implementer":"…","specReviewer":"…","qualityReviewer":"…","explorer":"…"}`). Free-form, host-specific values; the CLI never validates them, only surfaces the map in `orient`/`handoff` so the parent can apply it when spawning subagents. Absent → nothing changes.
- `settings.incubatorFile` — when set (by `tidy --externalize`), the Idea Incubator lives in this file instead of `ROADMAP.md`.
- `settings.branchPattern` — default `roadmap/{id}`; also matches `roadmap/{id}-<suffix>`. Maps item branches for discovery.
- `settings.staleDays` — default `7`. An item branch whose last commit is older than this is `stale` rather than `building`.
- `settings.integrationBranch` — default unset (work merges straight into trunk). Names the branch item branches merge into before trunk (e.g. `roadmap/v0.8.0`), or a list of names and fnmatch globs (`["fix/trunk-*", "roadmap/v0.8.0"]`) expanded against local branch names (case-sensitive; the trunk never matches). An item branch whose tip any matched branch contains but trunk does not reads `landed`; `landedIn` is that branch (the newest-committed when several contain it). Patterns naming the trunk or matching no local branch are ignored. Cost: one `for-each-ref --merged` call per matched branch, only when refs change.
- `settings.runsKeep` — default 200. How many lines `.roadmap/runs.jsonl` keeps; `run` trims older lines after each append.
- `settings.claimTtlHours` — default `12`. A claim with an owner refreshed within this many hours is **held** (see "Claim owners" below); `0` turns holds off.
- `settings.wipLimit` — default unset (no limit). When more items are in flight (`counts.lanes.inFlight`: unfinished with a branch or a claim) than this, `status`, `next` and `orient` print one `work in progress: N in-flight items, over settings.wipLimit (L)` warning line, `status --json` carries `wip: {count, limit, over}` (absent while unset), and the dashboard's "in flight" header chip turns red. A warning only — nothing is refused.
- `settings.worktreeWarn` — default `20`. The dashboard worktree panel header turns red, and `status --worktrees` says `over worktreeWarn`, when the repo has more linked worktrees than this.
- `settings.slots` — optional numbered sequences (DB migrations, ADR numbers, ports) that `slot` reserves per plan. `{"<kind>": {"glob": "packages/db/drizzle/*.sql", "pattern": "^(\\d{4})_", "width": 4}}`: `glob` selects files relative to the project root (`*` stays in one directory, `**/` spans directories), `pattern` is searched in the file **name** and its first group is the number, `width` zero-pads (default: the width of trunk's highest file). Absent → the feature is dormant and `status` / the dashboard are unchanged.
- `settings.forecastDays` — default `14`. The pace window for the version forecast (plan 44): steps ticked per day, dated by the `(YYYY-MM-DD)` stamp on each step's evidence line; a checked step without one is dated by the git commit that ticked it (read only for plan files written inside the window, cached on HEAD). The window shrinks to the project's history when that is shorter. `status` prints the forecast on each version header and `status --json` carries `forecast` keyed by version: `state` (`forecast` | `insufficient` with fewer than 5 ticks — "not enough history" | `done` at zero steps left), `remaining`, `ahead` (steps left in earlier open versions — versions are assumed to finish in order), `pace`, `sd`, `ticks`, `windowDays`, `days`, `date`, `range` (`[fast, slow]` from pace ±1 standard deviation of daily ticks; `slow` is null when pace − sd ≤ 0), `target`, `targetStatus`, `burndown` (steps left at the window start and the end of each day). Shipped versions below current are omitted.
- `settings.versionTargets` — optional `{"0.21.0": "2026-11-15"}`. Grades the forecast: `on track` (expected finish on/before the target), `at risk` (expected after it, but the fast end of the range makes it), `late` (even the fast end misses, or the date has passed with steps left). Ungraded while there is not enough history.

## Plan frontmatter
- `id, title, type (feature|bug|refactor|chore), version, status, created`
- `status` is DERIVED by `sync` from checkboxes: planned (0 done) / active (some) / done (all).
- **Claim keys** (optional, flat `claim_*` keys) — `claim_stage` (`review|fixing|gate-ready|gating|blocked|landed`), `claim_verdict` (`CONFIRMED|PARTIAL|REFUTED`), `claim_note`, `claim_branch`, `claim_landed_sha` (full sha of the commit the work landed in; kept only while the stage is `landed`), `claim_updated`, `claim_owner` and `claim_refreshed` (who holds the item and the UTC time they last claimed it, e.g. `2026-10-23T14:05:09Z`; see "Claim owners"). Written only by `roadmap.py claim <id>… --stage … [--verdict] [--note] [--branch] [--owner] [--take]` (several ids share the options, all-or-nothing) and `claim [<id>…] --landed <sha>` (keeps the owner as is); `claim <id>… --clear` removes them, and `check` ticking the final step on trunk removes them automatically. Flat keys because the frontmatter parser is line-based (no nesting). Never hand-edit.
- **Slot keys** (optional, flat `slot_<kind>` keys) — `slot_migration: 0269_domain_routing` (several numbers comma-separated: `0269_a, 0270_a_rls`). Written only by `roadmap.py slot <id> --kind K [--name N] [--add]`; `--release` removes one. They stay after the item is done (history) but done items drop out of the slot listing.
- **Follow-up keys** (plan 46) — `follow_up_of: 7` on a follow-up item's plan, `follow_ups: 12, 13` on the original; mirrored in config as `followUpOf` / `followUps` (item ids). Written by `release --with-waiting` and `retarget --split` only.
- **Bug links** (optional, plan 47) — `foundIn: <id>` on a bug plan filed by `roadmap.py bug --found-in <done id>`, and `bugsFound: <id>[, <id>]` on that origin plan (two-way link). Written only by `bug`. `status --json` items carry `foundIn` (int or null), `bugsFound` (ids) and `foundDuringBuild` (bullet texts of the plan's `## 🐞 Found during build` section, where `bug --found-in <in-flight id>` records each Fix step it appends); the dashboard plan page shows them.
- **Acceptance ledger** (plan 43) — each top-level bullet of `## ✅ Acceptance` is a criterion, except bullets labelled `**Fails …:**` (guards). `roadmap.py accept <id> --line N --evidence E [--fail]` writes `  > accepted: <date> E` (or `  > failed: …`) under bullet N, replacing an earlier marker; the last marker under a bullet wins. Blockquote sub-lines never parse as steps, so progress is untouched. `parse_plan()["acceptance"]` lists `{n, kind, label, text, state, date, evidence}`; `status --json` items carry `acceptance: {met, failed, total}` (criteria only); the dashboard adds `bullets` and shows `met/total accepted` on cards and each bullet's state and evidence on the plan page.
- **`approval: required`** (optional, hand-set) — the plan needs an owner sign-off: until a ruling tagged `approval` exists, `status --json` sets `needsApproval: true` and the dashboard shows a red "needs approval" marker.

## Waiting steps and follow-ups (plan 46)
- A **waiting step** is built but only verifiable after time passes (soak, DNS/cert propagation, billing cycle, store review): `- [~] Step 3: text (waiting until 2026-10-30: soak)`. Written by `wait <id> --step N --until <date|7d|2w> [--reason R]`; `wait … --clear` reverts it to `[ ]`. It **never counts as done**: `parse_plan` yields it as `(False, text)` (marker stripped) plus `waiting = {step: {until, reason}}`, so progress, changelogs, version completion, the forecast and the template gate all read it as open. Older skill versions do not parse `[~]` as a step at all, so they also never count it done.
- `check --plan ID --step N` on a waiting step ticks it and drops the marker. `check --all-done` (and so `check --landed`) **skips** waiting steps — only an explicit `--step` ticks one.
- Lane `waiting`: every step is ticked except waiting ones. It ranks right after `done` (above claims and branches), is not in flight, and counts as `counts.lanes.waiting`. `status --json` rows add `waiting` (count) and `waitingSteps` (`[{step, text, until, reason, daysLeft}]`); top-level `waitingDue` (steps due today or overdue, most overdue first) appears only when some item has a waiting step. `orient`, `next` and `status` print those due steps first; `next` skips a waiting item until a wait is due, then picks it first. ROADMAP.md shows `— 67% (+1 waiting)`.
- `release --version V --with-waiting`: items whose only open steps are waiting steps (and at least one step ticked) ship as complete; each one's waiting steps move into a **follow-up item** `Follow-up: <title> — verify after <reason>` in V. Without the flag `release` refuses and names the waiting steps.
- `retarget <id> --version V --split` (alias of `--to`): the ticked steps stay — the item completes in its own version — and every open step (waiting ones included) moves into a follow-up `Follow-up: <title> — remaining steps` in V. Needs ≥1 ticked and ≥1 open step; plain `retarget` is unchanged.
- A follow-up gets the next id, its own plan file (Core objective / Acceptance filled, so the template gate passes) and config entry. Moved steps are renumbered, keep their waiting marker and evidence lines, and leave `- ↪ Moved to follow-up #N (vV): <step>` in the original. The original's claim is cleared once it is complete.

## Claim owners
- Every `claim` records an owner: `--owner NAME`, else `$ROADMAP_OWNER`, else `git config user.name`, else the agent named by the environment (`claude`, `gemini`), else none. Set `ROADMAP_OWNER` per session when several sessions share one git identity.
- A claim is **held** while it has an owner and `claim_refreshed` is within `settings.claimTtlHours` (default 12). Any `claim` by the holder refreshes it.
- `claim` (and `claim --clear`) on an item held by a different owner (case-insensitive) is refused, naming the owner and claim age, unless `--take`. A multi-id claim stays all-or-nothing. A claim with no owner — written before owners existed, or with no identity available — is never held, so it stays claimable by anyone.
- `claim <id> --owner NAME` with no `--stage` on an unclaimed item opens an **owner-only** claim: it holds the item and counts as in flight while the lane stays derived (`planned` / `active` / `building`). Without `--owner`, a new claim still needs `--stage`.
- `next` skips items held by another owner (`skipping FEAT-5 (held by alice, 2h)`; `--force` overrides `dependsOn` only, never a hold). `orient` prints `Held by you (<owner>): …` and its JSON carries `owner` and `held: [{id, displayId, title, lane, age}]`.
- The dashboard shows `owner <name>` on in-flight cards (hover: claim age) and in the plan page's claim facts.
- Advisory only: no file or branch locking, no network identity.

## Rulings
- Dated decisions live in the plan **body**, never in frontmatter, config, the changelog, or ROADMAP.md: `- **Ruling (2026-10-22, owner[, approval]):** text`. `roadmap.py ruling <id> --text "..." [--by owner|<name>] [--approval]` appends one under a `## ⚖️ Rulings` section (created at the end of the plan when missing) and touches only the plan file. Append-only: to fix or drop a ruling, edit the plan by hand. `note` stays the changelog line and is not for decisions.
- Hand-written rulings anywhere in the body parse too: `**Ruling (date, who[, tags]):**`, `**Ruling date (who):**`, `**Owner ruling (date):**` (the one-word prefix is the author), `**...**:` with the colon outside, and the plural `**Owner rulings (date):**` over a nested list (items join with " · "). Tags after the author become `context`; `approval` / `approved` / `sign-off` mark a sign-off. Fenced code and HTML comments are skipped; prose mentions ("owner ruling 2026-10-17") are not rulings.
- `status --json` items and `/api/item` carry `rulings: [{date, by, text, approval, context}]` (file order) and `needsApproval`; the dashboard item card shows a `⚖ N` badge (✓ when approved) and the plan page lists them, approvals flagged.

## Numbered slots
- `slot <id> --kind K` reserves **max + 1** under a lock in the git common dir (shared by every worktree of the clone), where max covers: trunk's files for the kind, files added on any unmerged branch, the working tree, and every `slot_K` reservation in this checkout's plans, trunk's plans, and other worktrees' plans. No two reservations can receive the same number. Re-running it returns the held reservation (idempotent); `--add` reserves one more.
- Match state per item and kind (`status --slots`, `status --json` `slots`, dashboard strip): `ok` — the item's branch (claim branch, else discovered) adds every reserved number and nothing else, or the numbers landed on trunk (merged branch, or a trunk file named `<number>_<name>`); `missing` — no branch yet, or the branch has not added the file; `clash` — another item holds the same number, another item's branch adds this number, or this branch adds a number it did not reserve; `taken` — trunk already has the number from other work. Commits tagged only for *other* plans (stacked branches) are not counted against an item.
- `slot [<id>] --check [--json]` exits 1 on any `clash` or `taken` (scoped to one item when given); `missing` passes. Git cost: one `git diff trunk...branch` plus one `git log` per reserving branch, and one `git log` across all branches, cached on the tip shas.

## Lanes and branch discovery
- Each item has a derived **lane** (`status` JSON `item.lane`), first match wins: `done` > `waiting` (only waiting steps left; plan 46) > claim `stage` > `landed` (its branch has work trunk lacks and a `settings.integrationBranch` match contains its tip) > `stale` / `building` (an item branch with commits trunk lacks, or `(plan N)` / `(bug N)`-tagged commits) > trunk status (`planned` / `active`).
- A tagged commit a branch only inherited — reachable from another branch whose tip is an ancestor of it (its base, or a branch merged into it), or, for a branch no integration branch contains, from any matched integration branch — never attributes its item to that branch. A feature branch cut from integration therefore does not take over the items already landed there.
- Lanes are display-only. `status` (planned / active / done) still comes only from trunk checkboxes.
- Discovery reads git only, never writes `.roadmap/`: branches matching `branchPattern`, and commits tagged `(plan N)` / `(bug N)` (case-insensitive).
- `status --json` adds per item `lane`, `claim`, `branch` (with full tip `sha`, and `landed` / `landedIn` = the integration branch that contains it / `landedSha` = that branch's tip); top-level `trunk` and `otherBranches` (unmerged branches tied to no item); `counts.byLane` and `counts.lanes` (`done` / `inFlight` / `active` / `planned`; `landed` counts as in flight).
- **Landed flow** — `claim --landed <sha>` moves every unfinished item whose branch has unmerged work, at least one own `(plan N)` commit, and a tip `<sha>` contains to stage `landed`, storing `claim_landed_sha`; with ids it lands exactly those (tags not required) or none. `check --landed` (dry run; `--yes` applies, `--evidence` is prefixed) ticks every step of each `landed` item whose landing sha **and** current branch tip (if the branch still exists) are ancestors of trunk, writes evidence naming the sha, and clears the claim. A derived-only `landed` lane is display: it disappears once trunk contains the branch, so record it with `claim --landed` before merging integration into trunk. Containment is one batched git call; done still derives from trunk checkboxes only.
- Filters: `status --open` (not done), `--in-flight` (has a branch or claim, not done), plus `--version` / `--type` / `--status`.

## Run log
- Record fields: `at` (when recorded, UTC), `startedAt` (`at` minus the duration), `kind` (`gate` | `suite`), `label`, `result` (`pass` | `fail`), `items`, `branches`, `durationSec`, `log` (http(s) URL or null), `failing` (test names), `shards` (`{name: pass|fail}`).
- `status --runs` lists runs newest first by `at` (file order breaks ties). `status --json` carries `runs` (newest 50) and `trunkHealth` once a run is logged or `settings.integrationBranch` is set (otherwise the payload is unchanged): `trunkHealth.shards` holds the latest trunk suite result per shard (a suite run without `--shards` is one shard named by its label; a suite run naming only non-trunk branches is ignored) with the failing names on failed shards, `green` (null before any suite run), and `ahead` — `[{branch, commits}]`, commits each integration branch holds that trunk lacks (empty when `integrationBranch` is unset).

## Worktree map
- `status --worktrees [--json]` lists every **linked** worktree (the main checkout and bare entries are skipped): path, branch (or the detached head), the item it belongs to (the item's discovered or claimed branch, else `branchPattern`) with that item's lane, dirty file count (`git status --porcelain` lines, untracked included), unmerged commits vs trunk, claim stage, and last commit age.
- **Safe to remove** = clean, not locked, not missing, not the trunk checkout, and its branch fully merged into trunk (or a detached head trunk already contains). Anything else shows why not (`2 dirty; 4 unmerged`, `locked`, `missing (git worktree prune)`). A branch only `landed` in integration is not safe: it is not in trunk yet.
- For each safe worktree the command (`git worktree remove <path>`) is **printed, never run**. No `roadmap.py` command removes a worktree or deletes a branch.
- JSON: `status(root, worktrees=True)` adds top-level `worktrees` = `{trunk, count, safe, warnAt, over, rows}`; each row has `path, branch, head, detached, locked, prunable, dirty, ahead, behind, merged, landedIn, lastDate, lastSubject, safe, reason, removeCmd, item, displayId, title, lane, stage`. Plain `status` / `status --json` leave it out (it costs one `git status` per worktree).
- Dashboard: a collapsible **worktrees** panel under the item list with the same rows, the same in every view; the header (`N linked · K safe to remove`) is red past `settings.worktreeWarn`. Safe rows show the removal command as text to copy.
- Cost: `git worktree list` once plus one `git status` per worktree, cached with a 10 s budget, so the 1 s dashboard tick runs no per-worktree git call more often than every 10 s (a quiet tick stays one `for-each-ref`). Unmerged counts come from the ref scan already cached on the ref list; detached heads add one batched `git log`, cached by sha.

## Branch conflict risk
- `status --conflicts [--json]` checks every open item branch (not done, carrying unmerged work) for files it changes vs trunk (`git diff --name-only trunk...branch`, renames counted as both paths). Two branches sharing changed files form an overlapping pair: the two items, the shared files (first 10, plus `fileCount`) and a risk.
- Risk: `high` = `git merge-tree --write-tree` (git >= 2.38) reports a conflict between the two tips (`conflictFiles`); `low` = shared files but the tips merge cleanly; `medium` = file overlap only (older git, or merge-tree could not decide). Pairs sort high first, then most shared files. Two branches landed in the same integration branch are skipped (already merged together there).
- Suggested merge order: items with no overlaps first, then fewest overlaps, then fewest high-risk ones, then id.
- Read-only: merge-tree runs in memory and writes only loose objects — no branch, index, worktree or HEAD changes.
- JSON: `status(root, conflicts=True)` adds top-level `conflicts` = `{mergeTree, checked, unknown, pairs, counts, order}`; each pair is `{a, b, risk, files, fileCount, conflictFiles}` with `a`/`b` = `{id, displayId, title, branch, items}`. Items sharing one branch are one node (`items` lists every id on it, `id` is the lowest), so an integration branch carrying many landed items is one merge, not N pairs. Plain `status` / `status --json` leave `conflicts` out.
- Dashboard: a collapsible **conflicts** panel (pairs by risk plus the merge order), and each plan page lists the items it overlaps with.
- Cost: changed files are cached on (trunk tip, branch tip) and merge results on the two tips, so unchanged refs run no git call and a moved tip recomputes only that branch and its pairs. Cold work runs up to 8 git calls in parallel. `rmlib.conflicts.changed_files(root, branch, base=None)` exposes the cached per-branch list (`base` = diff from another branch instead of trunk, for a branch's own work).

## Scope drift (plan 42)
- **Declared paths** — `parse_plan()["declaredPaths"]`: every path pattern in the plan's blueprint `**Files …:**` bullets (with indented continuation lines) and the `-> target:` part of checklist steps, first-seen order, deduplicated. Backticked tokens win: when a field has any, only those count; otherwise whitespace/comma-split tokens that look like paths (contain `/` or `*`, have a file extension, are a dotfile or a known bare file like `Makefile`). Parenthesized commentary, URLs and fenced code are skipped; `{a,b}` braces expand.
- **Matching** — a pattern matches at a path-component boundary anywhere in the repo path, so plans may name paths relative to a subfolder (`rmlib/parse.py` matches `skills/roadmap/scripts/rmlib/parse.py`). A trailing `/` is a directory; a name without one matches the file or a directory of that name; `*` stays in one component, `**` crosses them.
- `settings.scopeAllow` — optional list of extra always-allowed patterns, on top of the defaults (tests: `tests/`, `test/`, `__tests__/`, `test_*.py`, `*_test.py`, `*_test.go`, `*.test.*`, `*.spec.*`; lockfiles: `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `uv.lock`, `Cargo.lock`, `go.sum`, `*.lock`, …; roadmap state: `.roadmap/`, `ROADMAP.md`, `CHANGELOG*.md`). An entry `!pattern` removes that default instead (e.g. `"!*.lock"`). Absent → defaults only.
- **Off-plan** — for each open item branch (not done, carrying unmerged work), the files the branch itself changes that neither its plan's declared paths nor the allow list cover. "Itself": diffed from trunk, or — for a branch cut from a `settings.integrationBranch` — from that integration branch, or from its fork commit once it has landed there (`rmlib.conflicts.work_base` / `own_changed_files`), so work it only carries is not counted. Items sharing a branch are judged against all their plans; an integration branch also counts the plans of items landed in it. A plan that declares no paths reports **no declared scope** rather than flagging every file.
- `status --drift [--json]` prints the report (off-plan items first, most files first, then no-scope, then the clean ones on one line); never blocks anything — whether an extra file is justified is the reviewer's call. JSON: `status(root, drift=True)` adds top-level `scopeDrift` = `{checked, flagged, noScope, unknown, allow, items, byItem}`, each entry `{id, displayId, title, branch, items, base, declared, changed, offPlan, offPlanCount, noScope}`, and `byItem` maps item id → off-plan list (`null` = no declared scope); every checked item row gains `offPlan`. Plain `status` leaves both out.
- Dashboard: the payload carries `scopeDrift` (computed once from the trunk view); cards show a red `N off-plan` chip (hover lists the files) and the plan page lists the off-plan files, or says the plan declares no scope.
- Cost: reuses the conflict item's cached per-branch diffs (keyed on the tips), so unchanged refs run no `git diff`.

## Digest
- `digest [--since W]` compares a **baseline** with the working tree now: the newest first-parent commit at or before the window start (its `.roadmap/` config, plans and the incubator file, read in one `git cat-file --batch`). Completed items, ticked steps (matched by step text), claim stage/verdict moves, new plans and new ideas are snapshot diffs — intermediate states inside the window are not listed. A repo younger than the window has an empty baseline (everything is new); outside git only runs and the attention list report. Stale = an item branch that crossed `settings.staleDays` inside the window; blocked = a claim that moved to `blocked` (listed there, not under claims). New branches = unmerged branches whose first own commit is in the window. Runs come from `.roadmap/runs.jsonl` by `at`.
- `W`: `30m`, `3h`, `1d`, `2w`, a date (local midnight), an ISO time, or `last` (default). `last` reads a per-user stamp in the git common dir — `<.git>/roadmap-digest.json`, keyed by roadmap root and owner, shared by every worktree of the clone, never tracked — together with the state that run saw, so the next `last` diffs against exactly that (uncommitted changes count once). With no stamp yet it falls back to `1d`. Every CLI `digest` run rewrites it; `orient` keeps its own key in the same file; the dashboard reads it but never moves it.
- Needs attention (`rmlib/digest.py` `ATTENTION`, one function per check, in order): waiting steps due or overdue (`waitingDue`), REFUTED verdicts, blocked claims, failing trunk suite, WIP over limit, slot clashes, high-risk conflict pairs (only with `--conflicts` — cold cost is a `git diff` per open branch — and always on the dashboard, whose conflict cache is already warm), and in-flight or started plans whose required sections are still template text.
- Output: terminal text, `--format md` (Markdown for chat), `--json` (`since`, `until`, `label`, `baseline`, `completed`, `ticked`, `claims`, `stalled`, `newPlans`, `newBranches`, `runs`, `ideas`, `attention`, `counts`). `orient` adds `digest` (`since`, `label`, `summary`, `counts`, `attention`) and prints at most three lines. Dashboard: `#/digest/<3h|1d|3d|1w|2w|last>` via `/api/digest?since=`.

## Project registry
- Per user, outside every repo: `~/.roadmap/projects.json` (`$ROADMAP_HOME` overrides the directory). `{"version": 1, "projects": {"<abs root>": {"name", "lastSeen"}}}`. Every `orient`, `status`, `serve` and `check` run in a roadmap project records its root — a linked worktree records its main checkout — at most once a minute, written atomically. Any read or write failure is silent: a malformed file reads as empty (and is rewritten on the next record), an unwritable one is skipped; no command fails because of the registry. `~/.roadmap` has no `config.json`, so it never makes `$HOME` a project.
- `projects` lists it; each entry gets a URL-safe slug from its name (clashing names add a 4-char path hash). `projects --forget <slug|name|path>` removes entries; a project you run a command in again comes back.
- `serve --all`: `/api/projects` builds one card per entry from `status()` of that root only (no worktree scan), cached 10 s per project; a project's normal endpoints are mounted at `/p/<slug>/…`, its broadcaster created the first time it is opened and ticking (1 s) only while one of its SSE streams is open. Missing paths render greyed and are not mounted.

## Dashboard navigation (plan 49)

- Routes: `#/search/<q>` (full-text), `#/versions`, `#/version/<v>`, `#/graph`, beside `#/`, `#/board`, `#/ideas`, `#/changelog`, `#/digest/<W>`, `#/plan/<id>`, `#/idea/<n>`, `#/notes/<path>`. All read-only; the page builds every node with `textContent` / attributes (no HTML parsing).
- `/api/search?q=` runs the CLI `search` (item titles and notes, plan bodies, incubator bullets) plus `.roadmap/notes/*.md` (`search(root, q, notes=True)`; the CLI keeps its scope). Each hit carries the page it opens (`id`, `idea` index or note `path`), a snippet of up to 70 characters either side of the match and the match offsets. Plan and note files are only reported when `/api/note` would serve them (no symlink escapes). At most 300 hits (`truncated`), queries up to 200 characters. Enter in the list filter opens it.
- `/api/version?v=` — the version's status rows (grouped by lane on the page), its forecast, `versionDates`/`releaseNotes` entries, and the version's `## v<v>` section of the public and internal changelog renderers as an unreleased preview; the page also shows `next --version` / `release --version` commands to copy.
- `#/graph` draws `dependsOn` edges among items of open versions (any item not done) as inline SVG, layered left to right by longest dependency path, column order by barycentre. Only items with an edge are drawn (others are counted); done dependencies from older versions are faded context. An edge from an unfinished dependency into an unfinished item is blocking (red); blocked items get a dashed red border. Click or Enter on a node opens its plan.
- Keys: `/` search, `g` then `l`/`b`/`i`/`c`/`g`/`v` (list/board/ideas/changelog/graph/versions), `j`/`k` rows, `Enter` open, `Esc` back, `?` shortcut sheet; `Ctrl/⌘ K` (also the tab-row button) opens a palette that fuzzy-matches pages, versions, plans (display id, `#id`, title) and ideas. Single keys are inert while typing in a field or with a modifier held; the palette chord works anywhere.
- Plan pages list the likely next CLI commands as copy buttons (the shown text is what is copied): `next`, `check --plan N --step K` (first open step, and due waiting steps), `wait`, the lane's next `claim` move (`--stage review` / `gate-ready` / `fixing` / `gating`, `--landed <trunk>`; `--take` when `/api/item`'s `me` — the default claim owner — differs from the holder), `check --landed [--yes]` for landed items, `accept N --line K` for the first acceptance criterion not yet met (plus `accept N` to list the ledger), `slot` per configured kind, `ruling` (with `--approval` when one is required) and `bug --found-in N`.

## Invariants
- Never hand-edit the managed region of ROADMAP.md; run `sync`.
- All mutations go through `roadmap.py` (atomic writes; safe on partial failure).
- Checklist lines inside fenced code blocks are ignored by parsing/sync/import.
- Claims are advisory state about in-flight work. Only trunk checkboxes make a step or item done.
- A `[~]` waiting step is never done; only an explicit `check --step N` ticks it.
- `check --evidence` appends an indented blockquote sub-line (`  > evidence: <text> (<date>)`) under the checked step; it is never parsed as a step, so progress counts are unaffected.
