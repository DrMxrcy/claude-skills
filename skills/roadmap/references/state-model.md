# Roadmap state model

## Source of truth
- **Plan files** (`.roadmap/plans/NNN-slug.md`) — progress (the checklist) + frontmatter.
- **`.roadmap/config.json`** — project, currentVersion, nextId, item registry, settings.
- **`ROADMAP.md`** — rendered view; the region between `<!-- roadmap:auto:start -->` and `<!-- roadmap:auto:end -->` is regenerated by `sync` (including the current-version line and per-version breakdown). Fully-done versions strictly below `currentVersion` collapse to a one-line summary unless `settings.collapseShipped` is `false`. Everything else (title, Idea Incubator) is free-form and never rewritten by scripts — `idea`/`remove` only append single bullets under the Idea Incubator heading.
- **Incubator location** — bullets live under the Idea Incubator heading in `ROADMAP.md` by default, or in the external file named by `settings.incubatorFile` (usually `.roadmap/IDEAS.md`, created by `tidy --externalize`, which leaves one linked bullet on the dashboard). `idea`/`promote`/`remove` resolve the location via `incubator_file()`; `tidy` analyzes both.
- **`.roadmap/notes/*.md`** — long-form idea write-ups created by `idea --body/--body-file`, linked from their incubator bullet. Not tracked in the registry.

## config.json
```json
{"project":"NAME","currentVersion":"0.0.1","nextId":1,
 "items":[{"id":1,"slug":"auth-setup","title":"Auth setup","type":"feature",
           "version":"0.0.1","file":"plans/001-auth-setup.md"}],
 "versionDates":{"0.0.1":"2026-07-09"},
 "settings":{"autoCommit":true,"gitTagOnRelease":false,"collapseShipped":true,
             "autoRelease":"nudge"}}
```
- `versionDates` — stamped by `sync` the first time a version hits 100% (stable changelog/collapse dates).
- `settings.collapseShipped` — defaults to `true` when absent. With it `false` and the auto block over 150 lines, `orient`/`tidy` suggest turning it back on (the auto block never triggers the free-form length warning).
- `settings.autoRelease` — `off` | `nudge` (default when absent) | `auto`: what happens when the current version is 100% but uncut (nudge prints a release reminder from `check`/`next`/`orient`; auto runs `release` when a target version is known).
- `settings.requireEvidence` — defaults to `false`; when `true`, `check` refuses without `--evidence "<verify command + result>"` (`--undo` is never gated).
- `settings.requiredSections` — per-type override of the plan sections `check` requires to be filled (`{"bug":["Observed","Root Cause","Acceptance"],"feature":["Core objective","Acceptance"],…}`; defaults: bug = Observed, Root Cause, Acceptance; feature/chore/refactor = Core objective, Acceptance). A name matches a `##` heading (emoji-insensitive prefix) or else a `**Label:**` bullet. While one is still template — empty, a bare `-`, an unfilled `**Label:**`, or a whole-value `<…>` placeholder — `check` refuses (naming the sections and file) unless `--force`, which records `forced past empty template (…)` in the evidence line; `--undo` is never gated. A required section the plan lacks entirely is skipped (older plans stay checkable) unless the type is listed here explicitly; `[]` turns the gate off for that type. `tidy` lists unfinished stub plans (report-only).
- `settings.buildRoles` — optional map of quality-first build roles to model/agent names (`{"implementer":"…","specReviewer":"…","qualityReviewer":"…","explorer":"…"}`). Free-form, host-specific values; the CLI never validates them, only surfaces the map in `orient`/`handoff` so the parent can apply it when spawning subagents. Absent → nothing changes.
- `settings.incubatorFile` — when set (by `tidy --externalize`), the Idea Incubator lives in this file instead of `ROADMAP.md`.
- `settings.branchPattern` — default `roadmap/{id}`; also matches `roadmap/{id}-<suffix>`. Maps item branches for discovery.
- `settings.staleDays` — default `7`. An item branch whose last commit is older than this is `stale` rather than `building`.
- `settings.integrationBranch` — default unset (work merges straight into trunk). Names the branch item branches merge into before trunk (e.g. `roadmap/v0.8.0`), or a list of names and fnmatch globs (`["fix/trunk-*", "roadmap/v0.8.0"]`) expanded against local branch names (case-sensitive; the trunk never matches). An item branch whose tip any matched branch contains but trunk does not reads `landed`; `landedIn` is that branch (the newest-committed when several contain it). Patterns naming the trunk or matching no local branch are ignored. Cost: one `for-each-ref --merged` call per matched branch, only when refs change.
- `settings.worktreeWarn` — default `20`. The dashboard worktree panel header turns red, and `status --worktrees` says `over worktreeWarn`, when the repo has more linked worktrees than this.
- `settings.slots` — optional numbered sequences (DB migrations, ADR numbers, ports) that `slot` reserves per plan. `{"<kind>": {"glob": "packages/db/drizzle/*.sql", "pattern": "^(\\d{4})_", "width": 4}}`: `glob` selects files relative to the project root (`*` stays in one directory, `**/` spans directories), `pattern` is searched in the file **name** and its first group is the number, `width` zero-pads (default: the width of trunk's highest file). Absent → the feature is dormant and `status` / the dashboard are unchanged.

## Plan frontmatter
- `id, title, type (feature|bug|refactor|chore), version, status, created`
- `status` is DERIVED by `sync` from checkboxes: planned (0 done) / active (some) / done (all).
- **Claim keys** (optional, flat `claim_*` keys) — `claim_stage` (`review|fixing|gate-ready|gating|blocked|landed`), `claim_verdict` (`CONFIRMED|PARTIAL|REFUTED`), `claim_note`, `claim_branch`, `claim_landed_sha` (full sha of the commit the work landed in; kept only while the stage is `landed`), `claim_updated`. Written only by `roadmap.py claim <id>… --stage … [--verdict] [--note] [--branch]` (several ids share the options, all-or-nothing) and `claim [<id>…] --landed <sha>`; `claim <id>… --clear` removes them, and `check` ticking the final step on trunk removes them automatically. Flat keys because the frontmatter parser is line-based (no nesting). Never hand-edit.
- **Slot keys** (optional, flat `slot_<kind>` keys) — `slot_migration: 0269_domain_routing` (several numbers comma-separated: `0269_a, 0270_a_rls`). Written only by `roadmap.py slot <id> --kind K [--name N] [--add]`; `--release` removes one. They stay after the item is done (history) but done items drop out of the slot listing.

## Numbered slots
- `slot <id> --kind K` reserves **max + 1** under a lock in the git common dir (shared by every worktree of the clone), where max covers: trunk's files for the kind, files added on any unmerged branch, the working tree, and every `slot_K` reservation in this checkout's plans, trunk's plans, and other worktrees' plans. No two reservations can receive the same number. Re-running it returns the held reservation (idempotent); `--add` reserves one more.
- Match state per item and kind (`status --slots`, `status --json` `slots`, dashboard strip): `ok` — the item's branch (claim branch, else discovered) adds every reserved number and nothing else, or the numbers landed on trunk (merged branch, or a trunk file named `<number>_<name>`); `missing` — no branch yet, or the branch has not added the file; `clash` — another item holds the same number, another item's branch adds this number, or this branch adds a number it did not reserve; `taken` — trunk already has the number from other work. Commits tagged only for *other* plans (stacked branches) are not counted against an item.
- `slot [<id>] --check [--json]` exits 1 on any `clash` or `taken` (scoped to one item when given); `missing` passes. Git cost: one `git diff trunk...branch` plus one `git log` per reserving branch, and one `git log` across all branches, cached on the tip shas.

## Lanes and branch discovery
- Each item has a derived **lane** (`status` JSON `item.lane`), first match wins: `done` > claim `stage` > `landed` (its branch has work trunk lacks and a `settings.integrationBranch` match contains its tip) > `stale` / `building` (an item branch with commits trunk lacks, or `(plan N)` / `(bug N)`-tagged commits) > trunk status (`planned` / `active`).
- A tagged commit a branch only inherited — reachable from another branch whose tip is an ancestor of it (its base, or a branch merged into it), or, for a branch no integration branch contains, from any matched integration branch — never attributes its item to that branch. A feature branch cut from integration therefore does not take over the items already landed there.
- Lanes are display-only. `status` (planned / active / done) still comes only from trunk checkboxes.
- Discovery reads git only, never writes `.roadmap/`: branches matching `branchPattern`, and commits tagged `(plan N)` / `(bug N)` (case-insensitive).
- `status --json` adds per item `lane`, `claim`, `branch` (with full tip `sha`, and `landed` / `landedIn` = the integration branch that contains it / `landedSha` = that branch's tip); top-level `trunk` and `otherBranches` (unmerged branches tied to no item); `counts.byLane` and `counts.lanes` (`done` / `inFlight` / `active` / `planned`; `landed` counts as in flight).
- **Landed flow** — `claim --landed <sha>` moves every unfinished item whose branch has unmerged work, at least one own `(plan N)` commit, and a tip `<sha>` contains to stage `landed`, storing `claim_landed_sha`; with ids it lands exactly those (tags not required) or none. `check --landed` (dry run; `--yes` applies, `--evidence` is prefixed) ticks every step of each `landed` item whose landing sha **and** current branch tip (if the branch still exists) are ancestors of trunk, writes evidence naming the sha, and clears the claim. A derived-only `landed` lane is display: it disappears once trunk contains the branch, so record it with `claim --landed` before merging integration into trunk. Containment is one batched git call; done still derives from trunk checkboxes only.
- Filters: `status --open` (not done), `--in-flight` (has a branch or claim, not done), plus `--version` / `--type` / `--status`.

## Worktree map
- `status --worktrees [--json]` lists every **linked** worktree (the main checkout and bare entries are skipped): path, branch (or the detached head), the item it belongs to (the item's discovered or claimed branch, else `branchPattern`) with that item's lane, dirty file count (`git status --porcelain` lines, untracked included), unmerged commits vs trunk, claim stage, and last commit age.
- **Safe to remove** = clean, not locked, not missing, not the trunk checkout, and its branch fully merged into trunk (or a detached head trunk already contains). Anything else shows why not (`2 dirty; 4 unmerged`, `locked`, `missing (git worktree prune)`). A branch only `landed` in integration is not safe: it is not in trunk yet.
- For each safe worktree the command (`git worktree remove <path>`) is **printed, never run**. No `roadmap.py` command removes a worktree or deletes a branch.
- JSON: `status(root, worktrees=True)` adds top-level `worktrees` = `{trunk, count, safe, warnAt, over, rows}`; each row has `path, branch, head, detached, locked, prunable, dirty, ahead, behind, merged, landedIn, lastDate, lastSubject, safe, reason, removeCmd, item, displayId, title, lane, stage`. Plain `status` / `status --json` leave it out (it costs one `git status` per worktree).
- Dashboard: a collapsible **worktrees** panel under the item list with the same rows, the same in every view; the header (`N linked · K safe to remove`) is red past `settings.worktreeWarn`. Safe rows show the removal command as text to copy.
- Cost: `git worktree list` once plus one `git status` per worktree, cached with a 10 s budget, so the 1 s dashboard tick runs no per-worktree git call more often than every 10 s (a quiet tick stays one `for-each-ref`). Unmerged counts come from the ref scan already cached on the ref list; detached heads add one batched `git log`, cached by sha.

## Invariants
- Never hand-edit the managed region of ROADMAP.md; run `sync`.
- All mutations go through `roadmap.py` (atomic writes; safe on partial failure).
- Checklist lines inside fenced code blocks are ignored by parsing/sync/import.
- Claims are advisory state about in-flight work. Only trunk checkboxes make a step or item done.
- `check --evidence` appends an indented blockquote sub-line (`  > evidence: <text> (<date>)`) under the checked step; it is never parsed as a step, so progress counts are unaffected.
